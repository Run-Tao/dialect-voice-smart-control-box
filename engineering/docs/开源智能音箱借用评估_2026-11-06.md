# 开源智能音箱「借用」评估（2026-11-06）

**对象**：立创开源硬件平台《【新手向】ESP小智同学AI智能音箱》
`https://oshwhub.com/zk272761180/learn-from-espai-xiao-zhi-classm`
**用途**：DialectVoice 工程学导论项目（基于方言语音识别的智能家居语音转换装置）硬件选型参考
**结论**：**可以借，但只借「执行端 / 机电载体」，不要让它承担方言识别，也不要整体复刻固件。**

## 2. 与本项目现状的三处根本冲突

本项目现状取自 `docs/项目建议书_正式版.md`、`docs/技术路线修订说明.md`、`docs/v5方案设计.md`：

1. **定位冲突**：项目建议书把「**不改音箱固件、不依赖厂商 API**」写成核心卖点，交付物是「语音**转换装置**」。若把这台开源音箱当作被控对象并改其固件，等于自己造了音箱 → 「转换」变「集成」，开题报告、建议书、答辩故事线需整体重写。
2. **技术内核冲突**：小智的识别是服务端/云端 ASR，不是端侧离线命令分类。方言直接喂给它，准确率取决于所选 ASR 引擎，与本项目 1D-CNN + 温度标定 + 风险-覆盖拒识的全部工作无关，且违反 v5 的 R2「端侧、离线、低成本、低延迟」。ESP-SR MultiNet 也没有粤语模型，无法承接方言识别。
3. **工程可行性冲突**：该工程 2025-10 已宣布停更，而官方主线现在要求 IDF ≥ 6.0.1（5.x 不再支持）；6pin Type-C 不能烧录；必须 N16R8；页面 BOM/3D/预览均为空。对 2 个月、≤1000 元的课程项目，这些是纯消耗。此外现有模型是 **1.35 MB 纯 numpy** 推理，搬到 ESP32-S3 需用 ESP-DL / TFLM / 手写 C 重写整条 log-mel40+Δ+CMVN+256 帧插值+3 种子 CNN 链，等于另开一个项目。

## 3. 建议：三种「借」法，按推荐度排序

### 方案 A（推荐）— 借「执行端」，替换掉最脆弱的一环

**现状链路最脆弱处**：`扬声器播普通话 → 智能音箱二次识别 → 执行`。项目建议书 §九已把它列为风险（「智能音箱对播放音频识别不稳定」）。

**改法**：把这一环换成小智官方的 **设备端 MCP / MQTT+UDP 直接下发命令** 到 ESP32-S3（LED / SG90 舵机 / GPIO 是官方原生支持）。

- 保留现有主线：树莓派/PC + VAD + 1D-CNN + 拒识 + 三态决策，一行不动；
- 在 `runtime/control.py` 的执行后端里**新增一个 MCP/MQTT adapter**，与现有串口、继电器后端并列（不改动既有 backend）；
- 普通话播报保留为「给用户听的确认语音」，不再承担「给音箱下指令」的职责。

**为什么改动很小**：v5 S4(b) 已实现「动作优先 + 异步播报」，两遍路径默认 `broadcast_command: false`，普通话命令音频本就不计入对话完成延迟。架构本来就在往「动作直接下发」走，这个开源生态正好补上物理执行端。

**收益**：执行成功率从「声学二次识别，不可控」变成「网络指令，可控且可 ACK」；仍是局域网、可离线、不依赖厂商 API，不破坏 R2；还能顺手补上 v5 里挂着的「执行器 ACK 闭环」待办。
**代价**：引入局域网依赖；项目建议书 §四、§五、§九 中「播放给智能音箱执行」的三处表述需同步修订；答辩需说明「为何放弃声学转换」。

### 方案 B（次推荐）— 只借机电件，不投 PCB

- 取其音频链路选型经验（ES8311 + NS4150B + 4Ω/3W 喇叭 + 麦克风 + N16R8 的 PSRAM 要求），用**现成 ESP32-S3 开发板 + 面包板**搭，不打样这块 PCB；
- 3D 外壳开源可直接打印，工程导论答辩的「成品观感」加分明显；
- 许可注意：该工程 GPL-3.0 且禁止商业使用，课程项目没问题；但若改固件公开发布有 GPL 传染性。**优先直接用小智官方 MIT 仓库**可绕开。

### 方案 C（加分项，不改主线）— 当对照实验

现场同一句粤语指令，分别给「本项目端侧 CNN + 拒识」与「小智原生云端 ASR」，对比识别率 / 端到端延迟 / 是否联网。这是答辩里很有说服力的一组自测数字。
**注意**：服务端 README 那张「使用粤语交流」演示图只能证明社区有人做过，**不是方言识别率证据**，必须自己实测，不得写进 PPT 当能力承诺。

## 4. 若采用方案 A，落地顺序

1. **先别打样 PCB**。买一块小智官方支持列表里的 ESP32-S3 开发板（立创实战派 / ESP32-S3-BOX-3 / M5Stack CoreS3 等），刷官方 `main` 分支（IDF 6.0.1+ 或 6.1），先确认 WebSocket / MQTT+UDP 连通。
2. 用 `xiaozhi-esp32-server` 最简化 Docker 安装（本地 FunASR），验证设备端 MCP 的 LED / Servo / GPIO 能被服务端调用。
3. 在 `runtime/control.py` 加 MCP/MQTT backend；把 6 条命令映射到 6 个动作，做 ACK 回报与超时处理。
4. 保留三级降级：**MCP 下发 → 串口 ESP32-S3 直控 → 继电器**；现场另备预录演示视频。
5. 同步修订项目建议书 §四 / §五 / §九 的联动方式表述，并在测试报告里新增「执行成功率」的两种通道对比。

## 5. 必须提醒的坑

- **IDF 版本**：官方主线已弃用 IDF 5.x，立创这份 2025 年停更的固件别直接拿新 IDF 编；要么走官方主线 + 官方支持板型，要么把老 IDF 环境锁死。
- **板型 BSP**：`main/boards` 顶层未见该工程命名（推断），若无现成 BSP 需自己适配引脚，工作量不小。
- **硬件细节**：6pin Type-C 不能烧录（要烧录夹）、必须 N16R8（不带 PSRAM 启动崩溃）、CC1/CC2 空接不支持双头 C 线。
- **资料完整性**：页面 BOM / 3D 模型 / 设计图预览均为空，复刻前先去 Gitee 把固件与 BOM 下全核对；本环境未能打开 Gitee 核实。
- **许可**：GPL-3.0 + 禁止商业使用（该工程）vs MIT（小智官方）。优先官方仓库。
- **预算**：PCB 打样 + SMT + 3D 打印外壳 + 屏 + 喇叭会迅速吃掉 1000 元；现有方案估算 305–1085 元已接近上限，且该估算未实时核价。
- **学术诚信**：现有全部性能数字来自合成 TTS，真人命令正样本 0 条；引入新硬件不会改变这一点，报告须继续分开标注合成域 / 真实域。

## 7. 附：推理主机一定要树莓派吗（2026-11-06 追加）

**结论：不一定要。树莓派不是技术门槛，是「答辩时别人不追问」的门槛。**

### 7.1 真实算力需求（已核实）

- 模型 `v3_cnn_ensemble_vad.npz`：**359,203 参数**（3 种子 × 约 11.9 万），结构为 Conv1d(80→64,k5) → BN/ReLU/Pool → Conv1d(64→128,k5) → BN/ReLU/Pool → Conv1d(128→128,k3) → BN/ReLU → mean+max 池化 → FC(256→6)。
- 单种子前向约 **14.9 M 乘加（≈30 MFLOP）**，3 种子合计 **≈90 MFLOP/条**。
- `runtime/` 核心只 `import numpy`（mel 滤波器组与 DCT 在 `features.py` 里自带实现，**不依赖 scipy/librosa**）。`requirements.txt` 里的 scipy / librosa / sklearn / pandas / matplotlib / PyQt5 / Flask / luma.oled 属训练、UI、串口与显示，不是推理必需。
- 即：**任何能装 Python3 + numpy 的板子都能跑**，不存在「必须树莓派」的技术绑定。

### 7.2 更该先修的两件事（都能本地验证）

1. **推理全程 float64**：`runtime/v3_cnn_numpy.py` 的 `embed()` 开头 `np.asarray(x, dtype=np.float64)`，`collect_arrays()` 导出权重时也 `dtype=np.float64`。本机实测（同一份算力，仅换 dtype）：

   | 精度 | 单种子 | 3 种子 |
   |---|---:|---:|
   | float64 | 2.63 ms | 7.89 ms |
   | float32 | 1.59 ms | 4.77 ms |

   **本机快 1.65×**（7.89 → 4.77 ms，与 `bench_latency.json` 的 infer P50 7.6 ms 吻合，说明该基准可信）。ARM 的 Cortex-A53 **没有 FP64 的 NEON 向量化**，FP64 吞吐通常只有 FP32 的一半，因此**在树莓派/香橙派上收益预计大于本机的 1.65×**（推断，需实测）。
   → 建议先改这一处（3 个点），再谈买什么板子。

2. **13–16 ms 是 PC 数字**：`docs/v5方案设计.md` §9 第 13 条已写明「延迟为离线 CPU 测量，目标硬件（树莓派）上的真实值待实测」。换任何硬件都必须重测 P95，并分表报告「PC 口径 / 目标板口径」——这是 R8 学术诚信的要求，也是答辩最容易被追问的点。

### 7.3 选项对比（价格为量级估算，**未实时核价**）

| 选项 | 估 90 MFLOP 推理耗时（float32） | 成本 | 关键约束 |
|---|---|---|---|
| 现有笔记本 / 开发机 | 约 5 ms（实测同量级） | 0 | 观感是「一台电脑」，需在报告里定义「端侧 = 家庭内本地推理、不联外网」 |
| 旧安卓手机（Termux + numpy） | 约 10–25 ms | 0 | 自带麦/喇叭/屏/电池；Termux 实时采集与 PortAudio 需折腾 |
| 树莓派 4B | 约 25–45 ms | 350–450 | 生态最好、资料最多、有 3.5 mm 音频口；贵、功耗高（5V/3A） |
| 香橙派 Zero 3（H618，4×A53 1.5G） | 约 45–90 ms | 90–150 | 性价比最高、有 3.5 mm；社区资料少于树莓派 |
| 树莓派 Zero 2W（4×A53 1G） | 约 55–110 ms | 120–180 | **板载无 3.5 mm 音频孔**（需 USB 声卡）；512 MB 内存偏紧；float64 下会翻倍到 110–220 ms，风险高 |
| ESP32-S3 独立跑 | 300 ms 以上，且需重写 | 0（已有） | 无 numpy，整条 log-mel+Δ+CMVN+3 种子链要改 C/ESP-DL，等于另开项目 |

> 上表耗时是按 FLOPs 与各核 NEON 峰值估算的数量级，**未在对应硬件实测**，仅供筛掉明显不合适的选项；最终必须实测 P95。

### 7.4 建议路径

1. **开发期不买板子**：用现有机器把功能、指标、演示跑完（当前即如此），硬件不阻塞任何一件事。
2. **先做 float32 改造**，再决定是否需要更强算力——这一条可能直接让「便宜的板子够用」。
3. **演示前 2 周再移植**：选一块板子只做「搬运 + 实测 P95 + 现场稳定性」，PC 口径与板端口径**分表报告**。
4. **按答辩口径选板**：
   - 「端侧 = 不联外网、数据不出户」→ 笔记本/旧手机即可，**省下 350–450 元**；
   - 「要有独立小装置、能拿在手上」→ 优先**香橙派 Zero 3**（省钱）或**树莓派 4B**（生态与可信度）；
   - **不建议** Zero 2W 作为首选：没有 3.5 mm 音频孔，且 A53@1 GHz 跑 float64 的余量太小。
5. 若坚持要更小的推理开销：可评估「单种子 + 级联早退」（高置信直接判，否则再跑另两个种子），平均算力可降到约 1/3，但**会改变集成行为，必须重跑 483 条测试集与 FAR 标定**，不能只看速度。
