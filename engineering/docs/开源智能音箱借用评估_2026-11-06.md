## 2. 与本项目现状的三处根本冲突

本项目现状取自 `docs/项目建议书_正式版.md`、`docs/技术路线修订说明.md`、`docs/v5方案设计.md`：

1. **定位冲突**：项目建议书把「**不改音箱固件、不依赖厂商 API**」写成核心卖点，交付物是「语音**转换装置**」。若把这台开源音箱当作被控对象并改其固件，等于自己造了音箱 → 「转换」变「集成」，开题报告、建议书、答辩故事线需整体重写。
2. **技术内核冲突**：小智的识别是服务端/云端 ASR，不是端侧离线命令分类。方言直接喂给它，准确率取决于所选 ASR 引擎，与本项目 1D-CNN + 温度标定 + 风险-覆盖拒识的全部工作无关，且违反 v5 的 R2「端侧、离线、低成本、低延迟」。ESP-SR MultiNet 也没有粤语模型，无法承接方言识别。
3. **工程可行性冲突**：该工程 2025-10 已宣布停更，而官方主线现在要求 IDF ≥ 6.0.1（5.x 不再支持）；6pin Type-C 不能烧录；必须 N16R8；页面 BOM/3D/预览均为空。对 2 个月、≤1000 元的课程项目，这些是纯消耗。此外现有模型是 **1.35 MB 纯 numpy** 推理，搬到 ESP32-S3 需用 ESP-DL / TFLM / 手写 C 重写整条 log-mel40+Δ+CMVN+256 帧插值+3 种子 CNN 链，等于另开一个项目。

## 3. 建议：三种「借」法，按推荐度排序

### 方案 A（推荐）— 借「执行端」，替换掉最脆弱的一环

**现状链路最脆弱处**：`扬声器播普通话 → 智能音箱二次识别 → 执行`。项目建议书 §九已把它列为风险（「智能音箱对播放音频识别不稳定」）。

**改法**：把这一环换成小智官方的 **设备端 MCP / MQTT+UDP 直接下发命令** 到 ESP32-S3（LED / SG90 舵机 / GPIO 是官方原生支持）。

- 保留现有主线：树莓派/PC + VAD + 1D-CNN + 拒识 + 三态决策，一行不动；
- 在 `runtime/control.py` 的执行后端里**新增一个 MCP/MQTT adapter**，与现有串口、继电器后端并列（不改动既有 backend）；
- 普通话播报保留为「给用户听的确认语音」，不再承担「给音箱下指令」的职责。

**为什么改动很小**：v5 S4(b) 已实现「动作优先 + 异步播报」，两遍路径默认 `broadcast_command: false`，普通话命令音频本就不计入对话完成延迟。架构本来就在往「动作直接下发」走，这个开源生态正好补上物理执行端。

**收益**：执行成功率从「声学二次识别，不可控」变成「网络指令，可控且可 ACK」；仍是局域网、可离线、不依赖厂商 API，不破坏 R2；还能顺手补上 v5 里挂着的「执行器 ACK 闭环」待办。
**代价**：引入局域网依赖；项目建议书 §四、§五、§九 中「播放给智能音箱执行」的三处表述需同步修订；答辩需说明「为何放弃声学转换」。

### 方案 B（次推荐）— 只借机电件，不投 PCB

- 取其音频链路选型经验（ES8311 + NS4150B + 4Ω/3W 喇叭 + 麦克风 + N16R8 的 PSRAM 要求），用**现成 ESP32-S3 开发板 + 面包板**搭，不打样这块 PCB；
- 3D 外壳开源可直接打印，工程导论答辩的「成品观感」加分明显；
- 许可注意：该工程 GPL-3.0 且禁止商业使用，课程项目没问题；但若改固件公开发布有 GPL 传染性。**优先直接用小智官方 MIT 仓库**可绕开。

### 方案 C（加分项，不改主线）— 当对照实验

现场同一句粤语指令，分别给「本项目端侧 CNN + 拒识」与「小智原生云端 ASR」，对比识别率 / 端到端延迟 / 是否联网。这是答辩里很有说服力的一组自测数字。
**注意**：服务端 README 那张「使用粤语交流」演示图只能证明社区有人做过，**不是方言识别率证据**，必须自己实测，不得写进 PPT 当能力承诺。

## 4. 若采用方案 A，落地顺序

1. **先别打样 PCB**。买一块小智官方支持列表里的 ESP32-S3 开发板（立创实战派 / ESP32-S3-BOX-3 / M5Stack CoreS3 等），刷官方 `main` 分支（IDF 6.0.1+ 或 6.1），先确认 WebSocket / MQTT+UDP 连通。
2. 用 `xiaozhi-esp32-server` 最简化 Docker 安装（本地 FunASR），验证设备端 MCP 的 LED / Servo / GPIO 能被服务端调用。
3. 在 `runtime/control.py` 加 MCP/MQTT backend；把 6 条命令映射到 6 个动作，做 ACK 回报与超时处理。
4. 保留三级降级：**MCP 下发 → 串口 ESP32-S3 直控 → 继电器**；现场另备预录演示视频。
5. 同步修订项目建议书 §四 / §五 / §九 的联动方式表述，并在测试报告里新增「执行成功率」的两种通道对比。

## 5. 必须提醒的坑

- **IDF 版本**：官方主线已弃用 IDF 5.x，立创这份 2025 年停更的固件别直接拿新 IDF 编；要么走官方主线 + 官方支持板型，要么把老 IDF 环境锁死。
- **板型 BSP**：`main/boards` 顶层未见该工程命名（推断），若无现成 BSP 需自己适配引脚，工作量不小。
- **硬件细节**：6pin Type-C 不能烧录（要烧录夹）、必须 N16R8（不带 PSRAM 启动崩溃）、CC1/CC2 空接不支持双头 C 线。
- **资料完整性**：页面 BOM / 3D 模型 / 设计图预览均为空，复刻前先去 Gitee 把固件与 BOM 下全核对；本环境未能打开 Gitee 核实。
- **许可**：GPL-3.0 + 禁止商业使用（该工程）vs MIT（小智官方）。优先官方仓库。
- **预算**：PCB 打样 + SMT + 3D 打印外壳 + 屏 + 喇叭会迅速吃掉 1000 元；现有方案估算 305–1085 元已接近上限，且该估算未实时核价。
- **学术诚信**：现有全部性能数字来自合成 TTS，真人命令正样本 0 条；引入新硬件不会改变这一点，报告须继续分开标注合成域 / 真实域。

## 7. 附：推理主机一定要树莓派吗（2026-11-06 追加）

**结论：不一定要。树莓派不是技术门槛，是「答辩时别人不追问」的门槛。**

### 7.1 真实算力需求（已核实）

- 模型 `v3_cnn_ensemble_vad.npz`：**359,203 参数**（3 种子 × 约 11.9 万），结构为 Conv1d(80→64,k5) → BN/ReLU/Pool → Conv1d(64→128,k5) → BN/ReLU/Pool → Conv1d(128→128,k3) → BN/ReLU → mean+max 池化 → FC(256→6)。
- 单种子前向约 **14.9 M 乘加（≈30 MFLOP）**，3 种子合计 **≈90 MFLOP/条**。
- `runtime/` 核心只 `import numpy`（mel 滤波器组与 DCT 在 `features.py` 里自带实现，**不依赖 scipy/librosa**）。`requirements.txt` 里的 scipy / librosa / sklearn / pandas / matplotlib / PyQt5 / Flask / luma.oled 属训练、UI、串口与显示，不是推理必需。
- 即：**任何能装 Python3 + numpy 的板子都能跑**，不存在「必须树莓派」的技术绑定。

### 7.2 更该先修的两件事（都能本地验证）

1. **推理全程 float64**：`runtime/v3_cnn_numpy.py` 的 `embed()` 开头 `np.asarray(x, dtype=np.float64)`，`collect_arrays()` 导出权重时也 `dtype=np.float64`。本机实测（同一份算力，仅换 dtype）：

   | 精度 | 单种子 | 3 种子 |
   |---|---:|---:|
   | float64 | 2.63 ms | 7.89 ms |
   | float32 | 1.59 ms | 4.77 ms |

   **本机快 1.65×**（7.89 → 4.77 ms，与 `bench_latency.json` 的 infer P50 7.6 ms 吻合，说明该基准可信）。ARM 的 Cortex-A53 **没有 FP64 的 NEON 向量化**，FP64 吞吐通常只有 FP32 的一半，因此**在树莓派/香橙派上收益预计大于本机的 1.65×**（推断，需实测）。
   → 建议先改这一处（3 个点），再谈买什么板子。

2. **13–16 ms 是 PC 数字**：`docs/v5方案设计.md` §9 第 13 条已写明「延迟为离线 CPU 测量，目标硬件（树莓派）上的真实值待实测」。换任何硬件都必须重测 P95，并分表报告「PC 口径 / 目标板口径」——这是 R8 学术诚信的要求，也是答辩最容易被追问的点。

### 7.3 选项对比（价格为量级估算，**未实时核价**）

| 选项 | 估 90 MFLOP 推理耗时（float32） | 成本 | 关键约束 |
|---|---|---|---|
| 现有笔记本 / 开发机 | 约 5 ms（实测同量级） | 0 | 观感是「一台电脑」，需在报告里定义「端侧 = 家庭内本地推理、不联外网」 |
| 旧安卓手机（Termux + numpy） | 约 10–25 ms | 0 | 自带麦/喇叭/屏/电池；Termux 实时采集与 PortAudio 需折腾 |
| 树莓派 4B | 约 25–45 ms | 350–450 | 生态最好、资料最多、有 3.5 mm 音频口；贵、功耗高（5V/3A） |
| 香橙派 Zero 3（H618，4×A53 1.5G） | 约 45–90 ms | 90–150 | 性价比最高、有 3.5 mm；社区资料少于树莓派 |
| 树莓派 Zero 2W（4×A53 1G） | 约 55–110 ms | 120–180 | **板载无 3.5 mm 音频孔**（需 USB 声卡）；512 MB 内存偏紧；float64 下会翻倍到 110–220 ms，风险高 |
| ESP32-S3 独立跑 | 300 ms 以上，且需重写 | 0（已有） | 无 numpy，整条 log-mel+Δ+CMVN+3 种子链要改 C/ESP-DL，等于另开项目 |

> 上表耗时是按 FLOPs 与各核 NEON 峰值估算的数量级，**未在对应硬件实测**，仅供筛掉明显不合适的选项；最终必须实测 P95。

### 7.4 建议路径

1. **开发期不买板子**：用现有机器把功能、指标、演示跑完（当前即如此），硬件不阻塞任何一件事。
2. **先做 float32 改造**，再决定是否需要更强算力——这一条可能直接让「便宜的板子够用」。
3. **演示前 2 周再移植**：选一块板子只做「搬运 + 实测 P95 + 现场稳定性」，PC 口径与板端口径**分表报告**。
4. **按答辩口径选板**：
   - 「端侧 = 不联外网、数据不出户」→ 笔记本/旧手机即可，**省下 350–450 元**；
   - 「要有独立小装置、能拿在手上」→ 优先**香橙派 Zero 3**（省钱）或**树莓派 4B**（生态与可信度）；
   - **不建议** Zero 2W 作为首选：没有 3.5 mm 音频孔，且 A53@1 GHz 跑 float64 的余量太小。
5. 若坚持要更小的推理开销：可评估「单种子 + 级联早退」（高置信直接判，否则再跑另两个种子），平均算力可降到约 1/3，但**会改变集成行为，必须重跑 483 条测试集与 FAR 标定**，不能只看速度。

## 8. 附：改用 ESP32 做主控的可行性（2026-11-06 追加）

**结论：可行，但必须是 ESP32-S3 + int8 量化 + ESP-DL；经典 ESP32 / C3 / C6 不可行。移植工作量约 2–3 周。**

### 8.1 为什么必须是 S3（官方依据，已核实）

ESP-DL 官方 `operator_support_state.md` 把目标芯片分三类，原文：

1. **ESP32 / ESP32-C2 / ESP32-C3 / ESP32-C5 / ESP32-C6 / ESP32-S2 — no PIE instructions. All operators are implemented in C, which is significantly slower compared to PIE-accelerated targets.**
2. **ESP32-S3 — PIE V1**
3. ESP32-P4 / ESP32-S31 — PIE V2

官方 `benchmark_report.md`（esp-dl 3.3.10，955 个用例，以 ESP32 = 1.00x 归一）：

| 算子 | esp32 | **esp32s3** | esp32p4 |
|---|---:|---:|---:|
| Conv（78 用例） | 1.00x | **22.9x**（3.40–171） | 38.8x |
| MaxPool | 1.00x | 37.1x | 77.2x |
| Gemm | 1.00x | 2.36x | 5.52x |
| 全部用例总耗时 | 11,492,627 us | **963,491 us** | 320,829 us |

即：**同样一份量化模型，S3 比经典 ESP32 快约 12×，Conv 快约 23×**。用经典 ESP32 跑这个 CNN，基本没有工程意义。

### 8.2 量化鲁棒性实测（本项目数据，483 条未见表达组测试集）

在 PC 上对三个种子的 conv / fc 权重做 **per-output-channel 对称 int8 量化后反量化**（scale = max|w|/127），激活保持 float（近似 w8a32，**不是** ESP-DL 的 w8a8）：

| 版本 | argmax 准确率 | 接受率 | 接受样本准确率 | 平均置信度 |
|---|---:|---:|---:|---:|
| float64 原模型 | **0.8820** | 0.7950 | 0.9349 | 0.9411 |
| int8 权重 | **0.8820** | 0.7930 | 0.9347 | 0.9409 |

**483 条里 argmax 完全一致，接受率只掉 0.2 个百分点。** 说明这个 35.9 万参数的小模型对权重量化极不敏感。

需要如实标注的两点：
- 本次实测的**接受率阈值取 `v3_thresholds.json` 的 0.93**（`V3Predictor.load` 默认读该文件），不是部署口径 `v3_thresholds_vad.json` 的 0.945；
- float 版 argmax 0.8820 与项目记录 0.8799 相差 1 条（483 中的 1 条），可能来自本次走 float64 路径；不影响「量化前后一致」这一结论。
- **w8a8（激活也量化）已于 2026-11-13 在 PC 上做模拟验证**，结果见 8.8；但那是 numpy 模拟、不是 ESP-PPQ 产出的定点工件，8.5 第 2 步仍须在真实工具链上重做。

### 8.3 移植清单

| 模块 | 现状（Python/numpy） | ESP32-S3 上要做的事 | 量级 |
|---|---|---|---|
| 特征前端 | `runtime/features_v3.py`：pre-emphasis → 分帧 512/160 → hamming → rfft512 → mel40 → log → 整句 CMVN → delta(w=2) → 插值 256 帧，得 80×256 | C 重写；FFT 用 esp-dsp；mel 滤波器组 40×257 预算成常量表 | **3–5 天**（最易出 bug，必须与 numpy 逐样本对齐） |
| 模型 | `v3_cnn_numpy.py`：Conv1d(80→64,k5)→BN/ReLU/Pool→Conv1d(64→128,k5)→BN/ReLU/Pool→Conv1d(128→128,k3)→BN/ReLU→mean+max→FC(256→6)，×3 种子 | PyTorch 恢复权重 → **Conv1d 改写为 Conv2d(kernel=(1,k))** → ONNX(opset 18) → ESP-PPQ 量化 → `.espdl` → ESP-DL 推理 | 2–4 天 |
| 双核加速 | — | ESP-DL 的**双核调度只对 Conv2D / DepthwiseConv2D 生效**，因此上面「Conv1d 写成 Conv2d(1,k)」不仅是格式转换，还能白拿双核 | 0（顺带） |
| 拒识 | maxprob + kNN OOD（500×256 f16 参照池 250 KB） | OOD 部分只是余弦距离，C 实现很轻；池放 PSRAM | 1 天 |
| 决策/澄清 | `decision.py` + `dialog.py`（状态先验、期望代价、澄清一次） | 简化状态机，C 重写 | 1–2 天 |
| 音频 | `sounddevice` | I2S + ES8311（该开源工程的方案）或 INMP441 数字麦；播报走同一 CODEC | 2–4 天 |
| VAD | 能量 + 自适应噪声底 | 照搬（简单），或复用 ESP-SR 的 VADNet | 1 天 |

合计约 **10–17 个工作日**，占 2 个月项目的 1/3 到 1/2。

### 8.4 算力估算（未实测）

单种子前向 ≈ 14.9 M 乘加，3 种子 ≈ 44.8 M 乘加。ESP32-S3 为 240 MHz 双核 + 128-bit PIE，int8 下按有效 1–2 GMAC/s（单核，esp-dl 实测量级）估算：

- 3 种子推理 ≈ **25–45 ms**（双核 Conv 再快约 1.5×，可到 15–30 ms）
- 特征提取（rfft 512 × 约 100 帧 + mel + 插值）≈ **15–40 ms**
- 合计 ≈ **40–85 ms/条**，在 300 ms 预算内有余量（120 ms 静音挂起 + 推理 + 播报不等）

> 这是按 FLOPs 与 PIE 理论吞吐的估算，**未在硬件上实测**。第一件该做的事就是测这个数（见 8.5）。

### 8.5 开工前必须先做的三个验证（按顺序，越早越省）

1. **算力验证（半天）**：在 S3 上跑 ESP-DL 自带 example，或把模型随机权重导成 `.espdl` 跑一次前向，用 `esp_timer` 打印 ms。若 >150 ms，立刻停手改方案（降为单种子或换 P4）。
2. **w8a8 精度验证（1–2 天，不碰硬件）**：用 ESP-PPQ 在 PC 上做完整 w8a8 量化（校准集从训练集抽 100–200 条），跑 483 条测试集，对比 argmax / 接受率 / 平均置信度。**若接受率掉超过 3 个百分点，说明拒识阈值必须整套重标定**（v5 的双信号门限 `maxprob ≥ 0.309193 AND ood ≥ −0.022306` 是在 float 分布上搜出来的，量化后必然漂移）。
3. **特征前端数值对齐（2–3 天）**：C 版特征与 numpy 版在同一批 wav 上逐样本比对，要求相对误差 < 1e-3。这一步不过，后面所有精度数字都不可信。

### 8.6 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **拒识阈值漂移** | w8a8 后 softmax 分布变化，0.945 与双信号门限失效 | 整套重标定：重跑 500 条参照池 + 校准集；报告里区分「float 口径」与「量化口径」 |
| **Conv1d 支持** | ESP-DL 只列 `Conv`（ONNX），未明示 1D 支持 | 一律改写为 Conv2d(1,k)，数学等价且能拿双核 |
| **内存带宽** | 权重 int8 约 360 KB，逐层激活频繁读写 | 权重放 flash/PSRAM，激活放内部 SRAM；用 ESP-DL 的静态内存规划器 |
| **300 ms 预算** | 估算 40–85 ms 有余量，但 I2S 缓冲与快挂会吃掉一部分 | 实测 P95，不达标就单种子或降帧数 |
| **工作量** | 2–3 周，且特征前端最易出隐性 bug | 先做 8.5 三步验证，任何一步不过就退回「PC/树莓派 + ESP32 执行端」方案 |
| **答辩风险** | 换成 MCU 后，合成域指标仍不变（真人正样本 0 条） | 硬件不改变数据结论，报告须继续分表标注 |

### 8.7 建议的推进顺序

1. 买 **ESP32-S3-WROOM-1 N16R8** 开发板（不要经典 ESP32、不要 C3）；
2. 先跑 8.5 的第 1 步（算力），同时并行第 2 步（PC 上 w8a8）；
3. 两步都过，再投入特征前端 C 重写；
4. **保留 PC 版本作为对照**：答辩时「同一模型 PC 8 ms / S3 约 45 ms，准确率 0.882 对 0.88x」是很好的工程叙事，也符合 R8「指标可信」。

### 8.8 w8a8 PC 模拟验证（2026-11-13 补跑，483 条）

> 状态：用户已确认主控为 **ESP32-S3**。本节是 8.5 第 2 步的**前置代理验证**，用于判断「激活量化会不会毁掉精度」，不替代 ESP-PPQ 真量化。

**方法**（纯 numpy，BN 先折叠进 conv）：权重 per-output-channel 对称 int8（scale = max|w|/127）；激活 per-tensor 对称 int8，scale 由训练集前 300 条取各层 max|act|/127 校准（实测 [5.0451, 7.8271, 8.9409, 11.1441]）；卷积用 int32 累加后反量化回 float，FC 同理。即模拟 w8a8，**不是 ESP-DL 的定点 requant**。

| 版本 | argmax | 接受率@0.945 | 接受样本准确率 | 平均置信度 |
|---|---:|---:|---:|---:|
| float64 | 0.8820 | 0.7640 | 0.9377 | 0.9411 |
| w8a8 模拟 | **0.8799** | 0.7619 | 0.9348 | 0.9409 |

- **argmax 一致率 0.9979**（483 条中仅 1 条翻转）；接受率掉 0.21 个百分点。
- 置信度漂移：平均 |Δ| = **0.0020**，最大 |Δ| = **0.0482**。
- 结论：**激活量化不是阻塞项**，w8a8 路线在精度上站得住。但最大 0.048 的漂移相对 0.945 边界样本不可忽略，8.6「阈值整套重标定」这条由数据支持，不能只改数字。

**三处口径必须标清**：① 本节阈值 **0.945**，与 8.2 的 **0.93** 不同，两表不可横向比较；② 两节都只验了**单阈值**，而当前部署默认已是 **v5 双信号门限**（`maxprob ≥ 0.309193 AND ood ≥ −0.022306`），量化对 kNN-OOD 距离的影响**尚未验证**；③ 全部数字来自 edge-tts 合成粤语，真人命令正样本仍为 0 条。

**2026-11-13 落地进展（路线已改，ONNX/ESP-PPQ 弃用）**：改走**纯 C 内核 + 离线 int8 权重量化**，避免 esp-ppq 对 Python 3.13 的兼容风险，代码在 `DialectVoice_Engineering/firmware/`：

- 特征前端 C（预加重/分帧/hamming/rfft512/mel40/log/CMVN/Δ/插值）与 numpy 逐样本对拍：seq 最大绝对误差 **7.8e-5 ~ 2.8e-4**（判据 1e-3），三条样本全 PASS；
- int8 推理（BN 折叠 + per-channel 权重 + per-tensor 激活 + int32 累加）在 **483 条测试集上与 numpy 决策 483/483 一致，准确率 0.8820，与 float 版完全相同**；
- 单种子（`DV_ACTIVE_SEEDS=1`）：**0.8592**（掉 2.3 pp），换来 2.9× 速度——若实机超时，这是第一个可调旋钮；
- 固件工程（ESP-IDF 5.4.1 / S3 / 16 MB flash / 八线 PSRAM）、串口协议（PING/INFO/RUNRAW）、烧录与对拍说明均已就绪，见 `firmware/README.md`。

**仍未做**：S3 实机 `esp_timer` 耗时（主机 gcc 口径约 107 ms/条，S3 估计 0.5–1 s，**大概率不满足 300 ms**）、I2S 麦克风接入、双信号拒识（含 kNN-OOD 池）搬移、阈值重标定、整机联调。性能要达标需 ESP-DL 的 PIE 路径或接受单种子降精度。
